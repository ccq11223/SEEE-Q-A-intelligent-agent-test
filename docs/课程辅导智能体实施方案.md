## 一、项目背景与目标

### 1.1 背景

学业指导中心对考试有困难、成绩偏低的同学提供一对一的课程辅导。现行流程是：学生申请帮扶 → 分配中心成员 → 学长学姐与学生见面摸底 → 制定复习计划。

这个流程里有五个反复出现的痛点：

- **摸底靠问，效率低。** 学长需要花一到两次沟通才能判断学生的真实水平，而这部分工作高度重复。
- **基础问题问不出口。** 成绩靠后的同学往往不敢问"定义是什么"这类基础问题，问题积压到考前才暴露。
- **资料散落、没被用起来。** 课程 PPT、串讲资料、往年题分散在个人电脑和群里，学长每次辅导都要重新翻找。
- **往年题有答案、没有解析。** 学生看懂答案也未必知道为什么，学长需要反复讲解同一类题。
- **资料是消耗品，不是资产。** 每一届学长积累的经验随人毕业而流失，没有人沉淀。

### 1.2 项目目标

构建一个**自研的课程辅导智能体**，用一条可复用的技术链路解决上述问题：

1. **把课程资料变成云端知识库。** 将 1000 页左右的课程 PPT/PDF 和往年题解析成结构化内容，切块、向量化后存入云端数据库，支持多人共同维护。
2. **让受助学生通过一个链接自助答疑。** 学生打开链接即可提问，回答必须带资料来源引用；资料没覆盖的问题，不编造，明确说明并转人工，同时记录下来供后续补充。
3. **第一次使用即产出学情报告。** 学生首次进入时完成 5 道分层诊断题，系统输出结构化《学情报告》给负责辅导的中心成员，降低前期摸底成本。
4. **让系统可以持续调教。** 提示词、试题、判卷规则、检索参数全部配置化并纳入版本管理，改动可追溯、可回滚。

### 1.3 本版明确不做的事

以下内容被有意排除在 v1.0 之外，目的是让第一版在一个人、用 AI 辅助开发的条件下真正做完：

- **不做多课程。** 第一版只服务一门课。但代码中"课程"是一等参数（`course_id`），后续增加课程只增加数据、不改架构。
- **不做学生账号体系。** 学生通过"链接 + 匿名代号"进入，系统不收集姓名、学号等身份信息。
- **不做自动出卷、不批改大题。** 诊断题由人工定稿，系统只负责抽题、判卷归类、写报告。
- **不做移动端 App。** 网页自适应即可，学生用手机浏览器访问。
- **不做 AI 替代人工。** 依据《张导_智能体小思考.docx》，人工见面沟通环节不可取消，系统只做前置工具。

### 1.4 成功标准

试点范围为 5-10 名本学期申请一对一帮扶的学生。达标线如下：

| 指标 | 目标值 |
| --- | --- |
| 建库覆盖率 | 课程核心章节 100% 有内容入库 |
| 检索命中率 | 黄金测试集（30-50 题）中 ≥ 80% 能检索到正确依据页 |
| 回答可追溯率 | 100% 回答带来源页码；无依据时必须显式说明 |
| 编造率 | 黄金测试集中 ≤ 5%，且全部被拦截为"转人工" |
| 诊断可用性 | ≥ 70% 的报告中"薄弱章节"与学长人工判断一致 |
| 学长增效 | 首次沟通前的摸底时间下降 ≥ 50% |
| 成本 | 一学期大模型 API 支出 ≤ 100 元 |

## 二、总体设计

### 2.1 一句话说明

这是一个**自研的单体应用**：一条离线流水线把课程资料变成云端知识库，一个在线服务让学生用链接答疑和做诊断，一个后台让你持续调教它。

### 2.2 三层结构

```
【第一层 · 离线建库】人工触发，跑一次，资料更新时重跑
   资料登记分级 → 结构化解析(公式/图表) → 人工抽查 → 清洗切块
   → 向量化入库 → 往年题解析生成与审核
                    ↓ 写入
【第二层 · 云端知识库】PostgreSQL + pgvector
   内容块(向量+页码) / 题目与解析 / 知识缺口 / 错题台账
                    ↑ 只读检索
【第三层 · 在线服务】常驻运行
   学生端：链接进入 → 5 题诊断 → 学情报告 → 答疑对话
           （检索 → 生成 → 引用 / 无依据则转人工）
   学长端：报告列表、知识缺口清单、错题台账、调教面板
           （本人登录，多人协作）
```

代码结构也按这三层切分，一个仓库、一个部署单元：

```
agent-code/
├── app/                    # 在线服务（FastAPI）
│   ├── api/                # 接口层：答疑、诊断、报告、后台
│   ├── core/               # 检索、生成、引用校验、转人工判定
│   ├── db/                 # 数据模型与访问层
│   └── web/                # 学生端与后台页面
├── pipeline/               # 离线建库流水线（命令行脚本）
├── config/                 # 提示词、诊断题组、规则、检索参数（YAML，纳入 git）
├── tests/                  # 单元测试 + 黄金测试集
├── docs/                   # 本方案与运维文档
└── data/                   # 原始资料与解析中间产物（不入 git）
```

### 2.3 端到端数据流

```
【学生】打开链接
   └─→ 输入匿名代号（不写姓名学号）
        └─→ 抽一套诊断题（5 题：2 概念判断 + 2 基础计算 + 1 小型综合）
             └─→ 逐题作答（可留下自己怎么想的）
                  └─→ 判卷归类（对学生作答匹配预设错误模式）
                       └─→ 生成《学情报告》→ 保存 → 给学长一条只读链接
                            └─→ 进入答疑对话
                                 ├─ 检索知识库 → 有依据 → 回答 + 引用页码
                                 ├─ 无依据 + 简单题 → 联网搜索 → 回答（强制标注"来自网络、未经审核"）+ 记入知识缺口
                                 └─ 无依据 / 复杂综合题 → 转人工话术 + 记入知识缺口

【学长】打开后台
   ├─ 看学情报告 → 人工核验后开展第一次沟通
   ├─ 处理知识缺口清单 → 审核候选解析 → 入库
   └─ 更新错题台账、调提示词与试题
```

### 2.4 五条关键架构决策

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| D1 | 单体应用，不做微服务、不做多课程、不做学生注册 | 一个人用 AI 辅助开发，组件越少越可能做完；学生要的是"链接就能用"，注册会拖慢落地 |
| D2 | 离线建库、在线只读 | 学生提问时绝不重新解析课件，避免延迟和重复成本；解析这类重活只做一次 |
| D3 | 知识库放云端，维护者用账号、学生用链接 | 满足"多人一起维护"；维护者需要登录和操作留痕，学生不需要 |
| D4 | 在线服务与离线流水线共用同一套代码与数据模型 | 否则解析逻辑会写两遍，日后改一处忘一处 |
| D5 | 所有可调内容配置化（YAML）并纳入 git | 这是"能不断调教"的落地方式：改动可追溯、可回滚、可多人协作 |

### 2.5 与《张导_智能体小思考.docx》的对应关系

文档中的要求已逐条落入本方案，但有两处**主动调整**，需要你知情：

| 文档中的表述 | 本方案的调整 | 原因 |
| --- | --- | --- |
| "主任负责维护 FastGPT 智能体配置"、"FastGPT 对话记录会留存" | 改为自研系统，后台由中心成员登录维护 | 你已明确要求完全自研。代价是维护内容从"平台配置"变成"自己的后台"，接手门槛更高，建议提前与张导对齐预期 |
| 未规定联网资料的呈现方式 | 学生可看到联网答案，但**强制标注"来自网络、未经审核"**，且仅限概念题与简单题；复杂题直接转人工 | 兼顾"学生不被卡住"与文档"防止错误知识输出"的红线。若后续试点中发现联网答案错误率偏高，可将该开关关闭，改为纯转人工 |

文档中其余要求（诊断题分层、报告四要素、免责声明、回答边界、按课程隔离、错题台账、隐私保护、小范围试点、例会复盘）均原样采纳，落点见第四章。

## 三、技术选型与 GitHub 现成组件调研

### 3.1 选型原则

**能用现成的绝不自己写。** 这个项目里真正需要你写的代码只有四件事（见 3.6），其余环节全部应该调用成熟开源项目或云服务。自研的价值在业务闭环，不在重新发明文档解析。

三条硬性筛选标准：

- **许可证可用。** 优先 MIT / Apache-2.0 / PostgreSQL 许可；AGPL-3.0 与自定义许可需要单独确认（本项目若开源发布，AGPL 不构成障碍；若打算闭源，则要避开）。
- **仍在活跃维护。** 优先近三个月有提交的项目，长期不更新的只作为备选。
- **部署成本低。** 能本地跑、不强制依赖 GPU 的项目优先，因为你只有一台普通机器。

### 3.2 调研方法与数据说明

下表数据于 **2026-10-15** 通过 GitHub API、项目主页与徽章接口实测抓取。需要说明三点：

### 3.6 结论：真正需要自己写的只有四件事

调研的结论很明确：**解析、向量化、数据库、网页界面、模型调用，全都有成熟组件可以直接调用。** 你自己要写的代码集中在下面四处，它们才是这个项目不可替代的部分：

1. **建库编排与资料分级。** 把上述工具串成一条命令，并实现"一级权威资料 / 二级需标注资料 / 三级待确认网络内容"的分级与来源标注。
2. **答疑决策链。** 判定"有没有依据"、校验回答里引用的页码是否真实存在、决定何时转人工、对计算类问题做双模型交叉校验。
3. **诊断模块。** 题组管理、把学生作答归类到预设错误模式、生成四要素学情报告。
4. **维护后台与调教配置。** 知识缺口清单、错题台账、配置化的提示词与试题。

## 四、功能详细设计

### 4.1 离线建库流水线

由你在本地手动运行，产出写入云端知识库。整条链路是"可重跑"的：某一份资料解析有问题，只重跑那一份。

**步骤 1：资料登记与分级。** 每个文件录入：课程、资料类型（课本重点 / 串讲 PPT / 老师划定考点 / 典型例题 / 往年题）、可信级别。级别只有三档：

- **一级（权威，可直接引用）**：课本重点、老师划定考点、中心往届串讲 PPT。
- **二级（可用，必须标注）**：典型例题、我们自己生成的往年题解析。
- **三级（不直接引用）**：网络来源。只存进"待确认区"，审核通过后升级为二级。

**步骤 2：格式规范化。** 按 3.3 的决策顺序，优先直读 PPTX/PDF；失败则先转 PDF 再解析。这一步的产物是中间文件，不入库、不进 git。

**步骤 3：结构化解析。** 输出 Markdown，要求三件事：公式保留为 LaTeX、表格保留为表格、图片抽出来单独存放并在原位留占位标记（形如 `[图 3-1：见 page_017_img_02]`）。这一步决定了后面所有问答的质量上限。

**步骤 4：人工抽查（不可省略）。** 按 5% 比例抽样检查解析结果，重点是含公式的页和纯图片页。抽查的作用不是"确保 100% 正确"，而是尽早发现系统性错误——比如某类公式全部转错，那就要换工具或换参数，而不是逐页修。抽查结果记入 `parse_errors` 表。

**步骤 5：清洗与切块。** 按章节标题的层级切块，单块长度控制在 300-800 字。每块必须带四个元数据：来源文件、页码、所属章节、可信级别。切块策略配置文件化，方便调教时更换。

**步骤 6：向量化入库。** 用 BGE-M3 生成向量（1024 维），写入 `chunks` 表。1000 页资料一次性完成，之后只在资料更新时增量重跑。

**步骤 7：往年题处理。** 这是知识库的第二类资产，也是最容易被低估的一步：

- 每道题拆出：题干、选项（如有）、标准答案、所属章节、年份。
- 用课件内容为它**生成解析**：要求解析必须引用具体页码，形成"答案为什么对"的推理链。
- **找不到课件依据的题**单独挑出来，进"知识缺口清单"，由你决定是否联网研究、人工补写，或标记为"仅提供答案、不给解析"。
- 有解析的题入库为二级资料；答案单独保留一份，供诊断模块判卷使用。

### 4.2 在线答疑（决策链是核心）

学生每次提问都走这条链，每一步都有明确的失败出口：

```
学生提问
  → ① 检索：向量召回 20 条 → 重排取前 5 条
  → ② 依据判定：最高相关度低于阈值？
        ├─ 否 → ③ 生成：把题目 + 检索到的原文 + 页码 + 回答规则交给模型
        │        → ④ 引用校验：回答中出现的页码必须存在于检索结果中，否则重新生成
        │        → ⑤ 返回答 + 引用 → 写日志
        └─ 是 → ⑥ 无依据分支
                 ├─ 概念题或简单计算题 → 联网搜索 → 回答
                 │      （顶部强制标注"以下内容来自网络搜索，未经审核，仅供参考"）
                 │      → 同时写入知识缺口清单
                 └─ 判定为复杂综合题，或联网也没找到 → 返回固定话术：
                        "这个知识点现有资料里没有覆盖，建议带着这道题找学长学姐线下确认。"
                        → 同时写入知识缺口清单
```

**针对电气专业课的两条额外防线**（这是《张导_智能体小思考.docx》最关心的风险）：

- **双模型交叉校验。** 对数值计算类问题（涉及具体数字、方程式求解），用第二个模型独立作答一遍。两者结论不一致时，**不展示任何一方结论**，统一返回"这道题两种解法结果不一致，建议线下确认"。这一条的运行成本极低，但对"公式错误误导学困生"这个最大风险非常有效。
- **引用强约束。** 模型不允许在没有检索结果的情况下自由发挥；回答里每个关键结论都要能对应到具体页码。做不到就降级为转人工。

**对话记录。** 每次问答落库：问题原文、命中的内容块 ID、最终回答、用了哪种模式（有依据 / 联网 / 转人工）、耗时、模型版本。这份日志是后面所有质量改进的数据来源。

### 4.3 诊断模块

**题组由你定稿，系统只负责抽题、判卷归类、写报告。** 这是保证诊断可靠性的关键设计——让 AI 现场出题，很容易出怪题、超纲题，甚至答案本身有错。

题组结构（每套 5 题，按文档要求分层）：

| 题号 | 类型 | 目的 |
| --- | --- | --- |
| 1-2 | 基础概念判断 | 判断"是不是根本没听懂" |
| 3-4 | 基础简单计算 | 判断"概念懂了但不会做题" |
| 5 | 小型综合题 | 定位"哪一部分章节薄弱" |

每道题除了标答，你还必须填**典型错误模式**。例如某道概念判断题，预设三种错法："把理想电流源当电压源处理"、"混淆参考方向与实际方向"、"忽略受控源"。判卷时模型做的是**归类**：把学生的作答匹配到"正确 / 错误模式 A / B / C / 其他"，而不是自由发挥点评。这样报告里的"薄弱章节"才有依据。

**《学情报告》四要素**（严格按文档要求，末尾固定加免责声明）：

1. 答对、答错的题号；
2. 判定薄弱的章节列表；
3. 建议优先复习的知识点（每条尽量挂上课件页码）；
4. 给辅导学长的提示，例如"该生基本概念模糊，需要从定义开始讲解，不宜直接刷难题"。

报告开头固定标注：**"AI 诊断结果仅供辅导同学参考，最终学情以人工沟通为准。"**

**交付方式。** 学生做完题生成一个只读报告链接，可设置 4 位口令，只有本次负责辅导的成员能看到。报告页不显示学生姓名学号，只用匿名代号。

**精度保障动作。** 题组上线前，你自己做一遍，再找 2-3 位同学试做，核对"判卷归类"和"薄弱章节判定"是否准确。这套动作每学期做一次，作为题组的定期校准。

### 4.4 维护者后台

学生端不做账号，**维护者需要登录**——这是"云端知识库、多人共同维护"的落地方式。用数据库自带的账号体系（Supabase Auth），设三级角色：

| 角色 | 权限 |
| --- | --- |
| 管理员（主任或组长） | 增删成员、改调教配置、导入资料、审核网络内容 |
| 课程负责人 | 该课程资料的导入与审核、试题维护、错题台账 |
| 普通成员 | 查看学情报告、提交错题、补充知识缺口 |

后台共四个页面：

1. **学情报告列表**——按学生、按日期查看诊断结果。
2. **知识缺口清单**——学生问过但资料没覆盖的问题，按出现次数排序，这是你决定"下一步补充什么资料"的最直接依据。
3. **错题台账**——记录：课程、问题原文、AI 的错误输出、正确答案、发现人、日期。对应《张导_智能体小思考.docx》第四节的要求。
4. **调教面板**——修改系统提示词、诊断题组、转人工规则、检索参数。所有修改写进 `config/` 下的 YAML 文件，通过 git 提交，形成可追溯的调教历史。

### 4.5 两个闭环

这个系统能不能越用越准，取决于下面两个循环是否真的转起来：

**知识缺口闭环**：学生问不到 → 记入清单 → 你批量联网研究 → 生成候选解析 → 你审核 → 入库成为二级资料 → 下次同类问题就能答了。

**错题闭环**：发现 AI 答错 → 记入错题台账 → 修正知识库内容或提示词 → **把这道题加入黄金测试集** → 以后每次改动都自动回归验证，防止同一个错误再犯。

第二个闭环里的"加入黄金测试集"是最容易被忽略、但价值最高的一步。没有它，调教就是在凭感觉改。

## 五、数据模型草案

全部落在云端 PostgreSQL 中，向量检索用 pgvector 扩展。v1.0 共 11 张表：

| 表名 | 作用 | 关键字段 |
| --- | --- | --- |
| `courses` | 课程（为将来多课程预留） | id, name, term |
| `documents` | 资料台账 | id, course_id, filename, doc_type, trust_level(1/2/3), status, parse_error_count |
| `chunks` | 知识库内容块（检索的基本单位） | id, document_id, page_no, section_title, content, embedding, trust_level, token_count |
| `questions` | 往年题与解析 | id, course_id, year, q_no, stem, answer, explanation, source_chunk_ids, review_status |
| `diagnostic_sets` | 诊断题组（多套轮换） | id, course_id, name, active |
| `diagnostic_items` | 题组内的单题 | id, set_id, order_no, type(concept/calc/synthesis), stem, options, answer, wrong_patterns(JSON), chapter |
| `student_sessions` | 学生匿名会话 | id, course_id, anon_code, created_at（不存姓名学号） |
| `diagnostics` | 诊断结果 | id, session_id, set_id, answers(JSON), result(JSON), report_token, created_at |
| `qa_logs` | 问答日志（质量改进的数据源） | id, session_id, question, retrieved_chunk_ids, answer, mode(kb/web/handoff), model, latency_ms, created_at |
| `gaps` | 知识缺口清单 | id, course_id, question, hit_count, status(open/researched/approved/rejected), web_candidate, approved_chunk_id |
| `error_ledger` | 错题台账 | id, course_id, question, ai_output, correct_answer, reporter, created_at, fixed |

另外有两个本地文件（不入库）：`config/*.yaml`（提示词、规则、检索参数、诊断题组源文件）和 `tests/golden/*.jsonl`（黄金测试集）。

## 六、部署方案与成本估算

### 6.1 两种部署形态

**形态 A（推荐起步）：本地跑应用 + 云端数据库。**

离线解析这类重活需要算力且只做一次，放在你自己的电脑上跑最省钱；在线服务先在本地运行，用内网穿透工具（如 Cloudflare Tunnel）把链接临时发给 5-10 名试点学生。

优点：零托管成本，随时可调试，出问题不影响任何人。

**形态 B（试点稳定后切换）：一台云服务器跑应用 + 云端数据库。**

用 Docker 在一台轻量云服务器上把服务跑起来，学生链接长期可用、开机即通。

无论 A 还是 B，**数据库始终在云端**，因此"多人维护"从第一天就成立——其他成员不需要在你电脑上装任何东西，登录后台网站就能看到报告、提交错题。

### 6.2 关于域名与备案

如果坚持用国内服务器 + 正式域名（`http://` 或 `https://` 的 80/443 端口），需要走 ICP 备案，个人主体一般 1-3 周，以学校名义备案时间更长。三个规避办法：

- 试点期直接用"服务器 IP + 非标准端口"（如 `:8000`）访问，不需要备案；
- 用 Cloudflare Tunnel 之类的隧道服务，绑定自己的域名对外，服务器仍在国内；
- 用海外免费托管平台，免备案但国内访问速度不稳定。

建议：**试点期用第一种或第二种**，等这套东西确实有用、要面向全年级时，再走正式备案。

### 6.3 成本估算

| 项目 | 用量假设 | 估算成本 |
| --- | --- | --- |
| 一次性解析（1000 页 PPT） | 本地运行开源工具 | 0 元（耗时约 1-3 小时） |
| 一次性解析（若改用云 API） | 1000 页 | 约 5-20 元 |
| 向量化 | 约 60 万 token | 0-5 元（用带免费额度的中文向量服务） |
| 往年题解析生成 | 约 300 题 | 约 3-8 元 |
| 日常答疑 | 每次约 5k 输入 + 1k 输出 | 约 0.01-0.02 元/次 |
| 日常答疑月支出 | 试点 10 人、每月 1000 次问答 | 约 10-20 元 |
| 云端数据库 | 免费层（数据量在数百兆内足够） | 0 元 |
| 云服务器（形态 B） | 轻量应用服务器或学生优惠机 | 约 10-40 元/月 |
| **合计（一学期约 5 个月）** |  | **约 50-250 元** |

价格以各平台当期官网为准；此表用于判断量级，不作为采购依据。**大模型调用这一项完全落在你"每学期几十元"的预算内**，服务器属于可选支出。

## 七、实施计划

每个阶段都以"能被独立验收"为边界。用 AI 辅助开发时，一次只做一件事、先写测试再写实现，是这个项目不跑偏的关键。

### 阶段 0：技术验证（1-2 天）

**目标**：在投入大量精力之前，先确认最容易失败的那一环能走通。

**主要任务**：

- 挑 3 页最典型的 PPT（含公式、含图表各一），跑通解析工具，肉眼检查公式是否还原正确；
- 用云端数据库建好 `chunks` 表，把这几页塞进去；
- 写一个最小脚本，问一个问题，看能不能检索到这几页并让大模型正确引用页码。

**交付物**：一份实测记录，写明哪个解析工具在这门课的 PPT 上效果最好、公式还原率大致多少。

**验收标准**：能从"提问"一路走到"回答带正确页码引用"。

**为什么先做这一步**：解析质量是整个系统的天花板。如果这里发现公式大量丢失，方案需要调整（例如改用视觉模型逐页转写），越早发现越好。

### 阶段 1：建库流水线（3-5 天）

**目标**：1000 页资料 + 往年题变成结构化知识库。

**主要任务**：实现 4.1 的七个步骤；产出资料台账、解析中间结果、`chunks`、`questions`、`gaps`；人工抽查 5% 并记录问题页。

**验收标准**：随机抽 20 个真实考点，其中至少 16 个能检索到正确的课件页。

### 阶段 2：答疑最小闭环（3-5 天）

**目标**：学生能通过链接提问并得到带引用的回答。

**主要任务**：实现 4.2 的决策链；三种模式（有依据 / 联网 / 转人工）都能触发；问答日志落库；学生端页面可用。

**验收标准**：把黄金测试集里 10 道"资料里根本没有"的题问一遍，**全部**走转人工或明确标注的联网分支，没有一道被编造。

### 阶段 3：诊断模块（3-4 天）

**目标**：5 题诊断 → 判卷归类 → 学情报告。

**主要任务**：题组与错误模式的数据结构；抽题逻辑；判卷归类；报告生成与只读链接；口令保护。

**验收标准**：自己按"全对""概念全错""计算全错"三种方式作答，报告能分别给出正确的薄弱章节与学长提示。

### 阶段 4：维护者后台（4-6 天）

**目标**：多人能协作维护。

**主要任务**：账号与三级角色；四个页面（报告列表、知识缺口、错题台账、调教面板）；配置化改造（把提示词、规则、题组移入 YAML）；git 提交规范。

**验收标准**：找一位中心成员，在不看你操作的前提下，独立登录并提交一条错题记录。

### 阶段 5：试点与迭代（2-3 周，持续）

**目标**：拿真实学生验证。

**主要任务**：按《张导_智能体小思考.docx》的流程接入 5-10 名帮扶学生；每次例会留 5-10 分钟复盘；收集学生使用感受与学长对诊断准确性的反馈；处理知识缺口清单。

**验收标准**：1.4 节的七项成功标准中，至少五项达标。

## 八、测试与质量保证

### 8.1 黄金测试集（最重要的一件基础设施）

建一个 30-50 题的固定题集，每题记录：问题、期望命中的资料来源、期望的结论要点。题集里必须包含 **10 道"资料里没有"的负样本**，用来验证系统会不会编造。

规则：**每次改动提示词、更换模型、补充资料之后，都跑一遍这个题集**，记录命中率与编造率。这是你判断"这次调教是变好了还是变坏了"的唯一客观依据。

### 8.2 必须专门测试的三类行为

- **拒答行为**：问一个课件里没有、网上也找不到的偏题，系统应转人工而不是硬答。
- **复杂题拦截**：问一道跨章节的综合大题，系统应按规则转为"建议线下辅导"，而不是输出一份看起来完整但可能错误的推导。
- **引用真实性**：抽查 20 条回答，逐条核对引用的页码里是否真的有对应内容。

### 8.3 上线前验收清单

- 学生链接在手机浏览器上能正常打开、答题、提问；
- 诊断报告链接加口令后，未持口令者无法访问；
- 对话记录中不含学生姓名、学号；
- 后台能查到任意一次问答的完整链路（问题、命中内容块、回答、模式）；
- 黄金测试集的编造率 ≤ 5%。

### 8.4 用 AI 辅助开发的工作方式建议

- 一个阶段一个分支，一个任务一次提交，提交信息写清改了什么；
- 每个功能先写测试再写实现——你不需要读懂所有代码，但需要能判断"测试有没有通过"；
- 让开发助手在动代码前先说清楚"要改哪些文件、为什么"，你确认后再改；
- 涉及密钥（数据库口令、模型 API Key）一律放环境变量，不写进代码、不提交到仓库。

## 九、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 解析质量差，公式和图片丢失 | 知识库从源头就不可靠，回答必错 | 阶段 0 先验证；人工抽查 5%；公式页单独用视觉模型或 Pix2Text 补识别 |
| AI 给出错误的公式或推导 | 学困生分辨不出，越学越错（文档重点关切） | 强制引用页码 + 双模型交叉校验 + 复杂题转人工 + 错题台账 + 黄金测试集回归 |
| 联网答案质量不可控 | 引入未经审核的错误内容 | 强制标注"未经审核"；仅限概念与简单题；一切网络内容须人工审核后才入库 |
| 学生过度依赖 AI | 违背帮扶初衷 | 按文档要求明确告知"AI 是辅助、不能替代思考"；保留人工见面环节；报告里附学习建议而非仅答案 |
| 隐私泄露 | 违反组织保密要求 | 不收集身份信息；报告用匿名代号 + 口令保护；对话日志可脱敏；明确禁止截图外传 |
| 许可证踩雷 | 项目发布或商用受阻 | 尤其注意 MinerU（AGPL 类）与 FastGPT（自定义许可），落地前逐个人工核实 LICENSE |
| 云端数据库访问慢 | 学生等待时间长 | 数据库仅被服务端访问；若实测延迟高，切换为国内轻量服务器自建 PostgreSQL + pgvector |
| 单人维护断档 | 项目随你毕业而停 | 配置全部配置文件化；写清运维文档；按文档建议把知识库校对工作分给课程掌握好的成员 |

## 十、后续拓展方向（本版不做）

以下方向在《张导_智能体小思考.docx》中被列为中长期构想。它们之所以容易实现，是因为 v1.0 的设计已经为它们留好了接口：

1. **薄弱章节自动推送串讲资料。** 学情报告里的薄弱章节如果能映射到具体内容块，就能直接附上对应串讲 PPT 的页码与片段。v1.0 的 `chunks` 表已经存了页码与章节，这一步几乎是顺带完成的。
2. **高频薄弱点统计。** `diagnostics` 表积累到几十份报告后，就能统计"哪一章是全年级普遍薄弱的"，为学院教学提供参考。
3. **多课程扩展。** 架构已按 `course_id` 参数化，新增课程是"加数据 + 加配置"，不是重写。
4. **面向全体低年级的"基础答疑模式"。** 在保证一对一帮扶优先的前提下，可开放一个只读问答入口。

## 附录 C：术语表

| 术语 | 含义 |
| --- | --- |
| 知识库 | 把资料切块并向量化后存入数据库，供检索使用的那份数据 |
| 内容块（chunk） | 知识库里的最小检索单位，通常是一段 300-800 字的文字，带页码等元数据 |
| 向量化 / embedding | 把文字转成一串数字，使语义相近的文字在数字空间里也相近，从而实现"按意思检索" |
| 检索增强生成（RAG） | 先检索资料、再让大模型基于检索到的原文作答，从而减少编造 |
| 引用校验 | 检查模型回答里提到的页码是否真实存在于检索结果中 |
| 转人工 | 系统判定无法可靠作答时，返回固定话术引导学生找学长学姐，而不是硬答 |
| 黄金测试集 | 一批固定问题和标准答案，每次改动后重跑，用于判断效果是变好还是变坏 |
| 知识缺口 | 学生问过但现有资料没有覆盖的知识点，累积成清单供你补充资料 |
| 错题台账 | 记录 AI 答错案例的清单，用于修正知识库并生成回归测试 |
